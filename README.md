## Taskman — консольное Todo-приложение на Go с использованием bubbletea

Мой первый мини-проект на Go для практики базы языка и дальнейшего перехода к написанию backend на нём.

Полноценный CRUD в терминале: создание, просмотр, редактирование и удаление задач с тегами и дедлайнами. Задачи хранятся в базе SQLite рядом с приложением.

Приложение состоит из двух частей: HTTP-сервер, который владеет хранилищем, и TUI, который ходит в него по сети как обычный HTTP-клиент. Что именно запустить — выбирается флагом `-serve`. Сервер поднимается первым: без него интерфейсу не с чем работать.

## Стек

- Go 1.25
- [charmbracelet/bubbletea](https://github.com/charmbracelet/bubbletea) — TUI-фреймворк (архитектура `Init` → `Cmd` → `Msg` → `Update` → `View`)
- `net/http` — HTTP API на стандартном `ServeMux` с маршрутами вида `GET /tasks/{id}` (роутинг по методам и параметры пути появились в Go 1.22, сторонний роутер не нужен)
- `database/sql` + [modernc.org/sqlite](https://gitlab.com/cznic/sqlite) — хранилище на SQLite. Драйвер написан на чистом Go, без CGO, поэтому проект собирается где угодно без внешнего компилятора
- Стандартная библиотека для всего остального: `encoding/json`, `time`, `slices`

## Запуск

```bash
git clone https://github.com/Lev2307/taskman.git
cd taskman
```

Нужны два терминала. В первом — сервер, он слушает `:8080` и владеет базой:

```bash
go run ./cmd/taskman -serve
```

Во втором — интерфейс:

```bash
go run ./cmd/taskman
```

Или собрать бинарник и запускать его так же — с флагом и без:

```bash
go build -o taskman ./cmd/taskman
./taskman -serve   # первый терминал
./taskman          # второй терминал
```

Файл `tasks.db` создаётся автоматически в рабочей директории сервера при первом запуске — схема разворачивается сама через `CREATE TABLE IF NOT EXISTS`, миграции накатывать не нужно.

## Возможности

- Создание задачи: заголовок, заметки, теги, дедлайн
- Список всех задач со статусом и дедлайном
- Карточка задачи: полная информация + сколько дней осталось до дедлайна (или на сколько просрочено)
- Редактирование задачи — форма открывается уже заполненной текущими значениями
- Отметка «выполнено» / «не выполнено»
- Удаление с подтверждением

## Хоткеи

**Главное меню**

| Клавиша | Действие |
|---|---|
| `1` / `a` | Создать задачу |
| `2` / `l` | Список задач |
| `3` / `ctrl+c` | Выход |

**Список задач**

| Клавиша | Действие |
|---|---|
| цифры | Ввод ID задачи |
| `enter` | Открыть задачу с введённым ID |
| `backspace` | Стереть символ |
| `esc` | В главное меню |
| `ctrl+c` | Выход |

**Карточка задачи**

| Клавиша | Действие |
|---|---|
| `e` | Редактировать |
| `space` | Переключить статус выполнения |
| `x` | Удалить (спросит подтверждение) |
| `esc` | Назад к списку |
| `ctrl+c` | Выход |

При подтверждении удаления: `y` — удалить, `n` или `esc` — отмена.

**Форма создания / редактирования**

| Клавиша | Действие |
|---|---|
| `enter` | Следующее поле, на последнем — сохранить |
| `↑` / `↓` | Перемещение по тегам |
| `space` | Отметить / снять тег (в блоке тегов), пробел в тексте (в текстовых полях) |
| `backspace` | Стереть символ |
| `esc` | В главное меню |
| `ctrl+c` | Выход |

Поля идут по порядку: заголовок → заметки → теги → дедлайн. Дедлайн вводится в формате `ГГГГ-ММ-ДД`, например `2026-12-31`.

Стандартные теги: `work`, `personal`, `sport`, `urgent`.

## HTTP API

Запускается флагом `-serve`, слушает `:8080`. Это единственный процесс, который читает и пишет `tasks.db`; TUI обращается сюда же. Тела запросов и ответов — JSON.

| Метод | Путь | Что делает | Успешный ответ |
|---|---|---|---|
| `GET` | `/tasks` | список всех задач | `200`, массив задач (пустой — `[]`) |
| `POST` | `/tasks` | создать задачу | `201`, созданная задача + заголовок `Location` |
| `GET` | `/tasks/{id}` | одна задача | `200`, задача |
| `PUT` | `/tasks/{id}` | заменить задачу целиком | `200`, обновлённая задача |
| `PUT` | `/tasks/{id}/done` | отметить выполненной / снять отметку | `200`, обновлённая задача |
| `DELETE` | `/tasks/{id}` | удалить задачу | `204`, без тела |

Правила по полям:

- при создании обязательны `title` и `dueAt`, причём `dueAt` не может быть в прошлом;
- `id` и `createdAt` назначает сервер — из тела запроса они не принимаются;
- при `PUT /tasks/{id}` идентификатор в теле должен совпадать с идентификатором в URL, а `createdAt` подставляется из хранилища;
- `PUT /tasks/{id}/done` принимает `{"done": true}` или `{"done": false}` — именно нужное значение, а не переключение, поэтому повторный запрос ничего не ломает.

Коды ошибок: `400` — нечисловой `id`, битый JSON или непройденная валидация; `404` — задачи с таким `id` нет; `405` — метод не поддерживается для этого пути; `500` — ошибка на стороне сервера.

Примеры (PowerShell, поэтому кавычки внутри `-d` экранируются обратным слэшем; в bash достаточно одинарных кавычек):

```powershell
curl.exe http://localhost:8080/tasks

curl.exe -X POST http://localhost:8080/tasks -H "Content-Type: application/json" -d '{\"title\": \"почитать про интерфейсы\", \"notes\": \"глава 7\", \"tags\": [\"work\"], \"dueAt\": \"2026-12-31T00:00:00Z\"}'

curl.exe -X PUT http://localhost:8080/tasks/1/done -H "Content-Type: application/json" -d '{\"done\": true}'

curl.exe -X DELETE http://localhost:8080/tasks/1
```

## Хранение

`tasks.db` — база SQLite из трёх таблиц:

| Таблица | Назначение |
|---|---|
| `tasks` | `id`, `title`, `notes`, `done`, `createdAt`, `dueAt` |
| `tags` | `id`, `name` с ограничением `UNIQUE` |
| `task_tags` | связка задачи и тега, составной первичный ключ `(task_id, tag_id)` |

Теги вынесены в отдельную таблицу, а не лежат строкой внутри задачи: имя тега хранится один раз, а `task_tags` связывает его с любым числом задач. Составной первичный ключ делает дубль пары невозможным, а `ON DELETE CASCADE` заставляет удалённую задачу унести свои связки за собой.

Время пишется строками RFC3339 в UTC. В таком виде лексикографическое сравнение совпадает с хронологическим, поэтому `ORDER BY dueAt` работает без всяких конвертаций. Задача без дедлайна хранит в `dueAt` `NULL`, а не нулевую дату — на стороне Go этому соответствует `nil *string` и нулевой `time.Time`.

Теги перед записью нормализуются: нижний регистр, обрезка пробелов, отсев пустых, дедупликация, сортировка. Сортировка тут не косметика — она делает порядок тегов у задачи детерминированным.

Соединение открывается с прагмами `journal_mode=WAL`, `busy_timeout=5000` и `foreign_keys=on`, пул ограничен одним соединением (`SetMaxOpenConns(1)`): параллельных писателей SQLite всё равно не любит, а очередь запросов внутри процесса дешевле, чем ловля `database is locked`. Операции, которые трогают и задачу, и её теги, идут одной транзакцией — иначе падение на середине оставило бы задачу с половиной тегов.

## Структура проекта

```
cmd/taskman/main.go        точка входа: TUI или HTTP-сервер по флагу -serve
internal/model/
  task.go                  структура Task и интерфейс TaskStore, который реализуют хранилища
internal/storage/
  sqlite.go                текущее хранилище: схема, все методы TaskStore, теги
  sqlite_test.go           тесты хранилища на временной базе
  json.go                  первая версия хранилища: tasks.json, Store с мьютексом
  json_test.go             тесты к нему
internal/api/
  server.go                Server со ссылкой на хранилище, Routes() — оглавление API
  tasks.go                 хендлеры эндпоинтов
internal/ui/
  store.go                 интерфейс TaskStore со стороны UI и Client — его HTTP-реализация
  app.go                   корневая модель, переключение экранов
  list.go                  список задач
  detail.go                карточка задачи
  create.go                форма создания и редактирования
```

Экраны — независимые модели со своими `Update` и `View`. Наружу они не переключают экраны сами, а отправляют сообщение (`BackToListMsg`, `RedirectToEditTask` и т.д.), которое обрабатывает корневая модель в `app.go` — она и решает, какой экран показать.

UI не знает, откуда берутся задачи: он работает через интерфейс `TaskStore` из `internal/ui/store.go`, а конкретную реализацию получает из `main.go`. Сейчас это `Client` — обёртка над HTTP API.

Развязка через интерфейс заодно закрыла реальный дефект. Раньше TUI и сервер были двумя процессами, писавшими в один и тот же `tasks.json`, а `sync.Mutex` внутри `Store` защищает только в пределах одного процесса — параллельная запись могла затереть чужие изменения. Теперь в хранилище пишет ровно один процесс.

Со стороны сервера интерфейс `TaskStore` живёт в `internal/model` — нейтральном пакете, который видят и `api`, и `storage`. `SQLiteStore` реализует его вторым после `Store` на JSON — и это уже третий по счёту случай, когда хранилище прячется за интерфейсом: со стороны UI ту же роль играет `Client` поверх HTTP. Переезд с файла на базу не потребовал правок ни в хендлерах, ни в UI: в `main.go` поменялась одна строка, которой создаётся хранилище. Старая реализация на JSON осталась в репозитории, вернуться к ней можно закомментированной строкой там же.
